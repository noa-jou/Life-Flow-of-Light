# Life Flow of Light — Structure and Technology

[Project overview](../README.md) · [繁體中文](StructureIntro.zh-TW.md)

This optional introduction explains how the project is organized and how its main technologies work together.

You do not need to understand every tool before trying the demonstration. For installation and startup instructions, see the [User Guide](UserGuide.md).

## 1. The big picture

Life Flow of Light is a software-only proof of concept.

The browser simulates household lighting. The backend records lighting activity in a local database. The frontend then displays that history and lets users search for possible Morse messages.

No physical smart bulbs or sensors are required.

| Part | Responsibility |
| --- | --- |
| Frontend | Displays the interface, handles user interactions, and sends HTTP requests. |
| Backend | Validates requests, manages bulbs, records activity, and interprets Morse patterns. |
| Database | Stores bulbs and lighting sessions in a local SQLite file. |

The frontend does not open the database directly. It asks the backend for data and displays the response.

### Fast Refresh and HMR

During development, Vite's hot module replacement (HMR) and React Fast Refresh help many code changes appear without a full page reload.

Some changes still require a reload. Interface state is not guaranteed to survive every edit.

The project uses `@vitejs/plugin-react`. The supplied configuration does not enable the alternative SWC plugin or React Compiler.

The optional ESLint extensions mentioned in the original template are not automatically included in this project.

### The four panels

| Panel | Purpose |
| --- | --- |
| Bulbs | Register, rename, install, uninstall, and delete eligible bulbs. |

The interface supports English and Traditional Chinese.

The frontend explains how to send a signal and displays the result. The backend decides how the recorded signal is interpreted.

## 5. What the database stores

The database contains two main tables.

| Table | Contents |
| --- | --- |
| `bulbs` | Bulb ID, permanent serial number, current name, and current installation position. |
| `light_sessions` | Bulb ID, position when the session began, first heartbeat time, and most recent heartbeat time. |

A bulb with a `null` position is registered but not installed.

A lighting session represents a continuous period of observed lighting activity.

The session stores:

- `started_at`: the first heartbeat time.
- `last_seen_at`: the most recent heartbeat time.

There is no separate `ended_at` field. Times are stored as Unix timestamps in milliseconds.

### Preserving meaningful history

The database schema:

- Allows only one installed bulb at each position.
- Allows multiple uninstalled bulbs.
- Prevents changing a registered bulb's serial number.
- Prevents deleting a bulb referenced by lighting history.

A historical session keeps the position recorded when it began, even if the bulb is moved later.

Morse messages are calculated from lighting sessions when requested. They are not stored in a separate message table.

## 6. How the frontend and backend communicate

During development, the browser sends API requests to paths beginning with `/api`.

Vite forwards those requests to:

`http://127.0.0.1:3000`

It removes the `/api` prefix before forwarding the request.

For example:

| Browser request | Backend route |
| --- | --- |
| `/api/bulbs` | `/bulbs` |
| `/api/heartbeat` | `/heartbeat` |
| `/api/light-sessions` | `/light-sessions` |
| `/api/morse/check` | `/morse/check` |

### A typical interaction

1. The user operates a virtual light.
2. While the light is on, the frontend sends repeated heartbeats.
3. The backend validates the request and creates or updates a lighting session.
4. The frontend requests stored sessions to display the history.
5. When the user searches for Morse messages, the backend analyzes recorded light durations and gaps.
6. The frontend displays the returned results.

The database records the underlying activity. The timeline and Morse search present different interpretations of that activity.

### Development and deployment

The Vite proxy is part of the local development setup.

A frontend build produces static browser assets. It does not include a running backend or database.

Deploying the built frontend elsewhere also requires a working backend and an appropriate API routing arrangement.

## 7. Development and build commands

This table explains the available commands. It is not the installation sequence.

Follow the [User Guide](UserGuide.md) for setup and startup steps.

| Folder | Command | Purpose |
| --- | --- | --- |
| `frontend/` or `backend/` | `npm ci` | Installs dependencies from that application's lockfile. |
| `frontend/` | `npm run dev` | Starts the Vite development server. |
| `frontend/` | `npm run build` | Runs TypeScript checks and builds browser assets. |
| `frontend/` | `npm run lint` | Runs ESLint. |
| `frontend/` | `npm run preview` | Previews the frontend build locally. It does not start the backend. |
| `backend/` | `npm run dev` | Runs the backend with file watching through `tsx`. |
| `backend/` | `npm run typecheck` | Checks application types without generating JavaScript. |
| `backend/` | `npm test` | Type-checks the tests and runs the test suite. |
| `backend/` | `npm run build` | Compiles backend TypeScript into JavaScript. |
| `backend/` | `npm start` | Runs the previously compiled backend. |
| `backend/` | `npm run seed` | Generates demonstration records for an empty database. |

`npm start` does not build the backend first. After changing backend source code, rebuild it before running the compiled version.

The seed command is an optional setup step, not a command to run every time the application starts.

### Different checks serve different purposes

| Check | What it helps verify |
| --- | --- |
| Type checking | Whether values and interfaces follow the declared types. |
| Linting | Whether code follows the configured rules. |
| Automated tests | Whether tested behavior matches expectations. |
| Manual operation | Whether the complete interface and workflow behave as intended. |

Passing one check does not guarantee that every part of the application works correctly.
